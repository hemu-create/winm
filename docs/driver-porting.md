# Driver Porting Guide: Asahi Linux to Windows

This guide maps Asahi Linux/M3 support to WinM's Windows driver work. It is a
planning document, not a complete port.

## Source of truth

- m1n1 ADT/FDT output for the target SoC.
- Asahi Linux kernel drivers and device tree bindings.
- m1n1 register definitions and initialization sequences.
- WinM ACPI tables generated by b00t.

## Porting rules

1. Do not copy GPL kernel driver code into MIT-licensed WinM components.
2. Use Asahi/m1n1 to discover register layouts, power sequences, and DT nodes.
3. Implement Windows drivers as clean-room WDF/KMDF or storport miniports.
4. Prefer inbox Windows drivers when ACPI can describe the hardware.
5. Keep SoC-specific code behind a platform abstraction.
6. Record the Asahi source file and version for every hardware fact.

## M3 (`t8122`) blocks

| Block | Asahi/m1n1 source | WinM target | Windows strategy |
| --- | --- | --- | --- |
| AIC | `m1n1/src/aic.c`, `aic_regs.h` | `hal-aic/`, b00t GIC emulation | Phase 1: virtual GIC; Phase 4: HAL extension research |
| DART | Asahi DART driver, m1n1 DT | b00t + storage miniport | 4K CPU pages, 16K-aligned DMA/bounce buffers |
| NVMe | Asahi NVMe + DART | `drivers/nvme/` | Storport miniport or b00t block service |
| USB DWC3 | m1n1 `usb_dwc3.c` | `drivers/usb/` | Inbox xHCI if ACPI describes it; custom driver if needed |
| Type-C PD | m1n1 `usb.c`, TPS6598x/CD321x | `drivers/usb/` | ACPI methods or custom PD driver |
| PCIe | Asahi PCIe driver | `drivers/pcie/` | ACPI `_CRS`/`_DSD` and power resources |
| PMU/SMC | Asahi SMC/PMU drivers | `drivers/pmu/` | Battery, thermal, fan, charger driver |
| SPI-HID | Asahi SPI-HID | `drivers/spi-hid/` | HID transport or dedicated input driver |
| DCP | Asahi DCP driver | `drivers/display/` | Display-only WDDM driver, Phase 4 |
| GPU | Asahi GPU driver | `drivers/display/` | Out of scope initially |
| Wi-Fi/BT | Asahi brcmfmac | future | Large firmware/driver effort |

## Device tree to ACPI mapping

For each Asahi DT node, b00t should generate or reference:

- compatible string;
- register base and size;
- interrupt parent and interrupt specifiers;
- power/clock dependencies;
- DMA constraints;
- status.

Windows drivers should not depend on Linux DT directly. b00t converts the
relevant facts into ACPI devices, `_CRS`, `_DSD`, and interrupt resources.

## Power sequencing

Asahi drivers often contain SoC-specific power and reset sequences. These
must be preserved in:

- b00t early initialization;
- ACPI power resources;
- Windows driver start/stop paths;
- recovery and reset paths.

Do not assume a Linux power sequence can be dropped; document and test each one.

## Interrupt mapping

Asahi uses AIC and Linux IRQ numbers. WinM maps AIC hardware IRQs to GIC
INTIDs in b00t. Windows drivers see only the emulated GIC. The mapping must be
recorded and tested under I/O load.

## DMA and DART

- Linux/Asahi can use 16K pages and DART-aware DMA.
- Windows uses 4K pages.
- Every ported driver must state its DMA alignment and buffer ownership.
- Prefer b00t-owned DART domains for bring-up.

## Function-level conversion notes

### AIC

Asahi/m1n1:
- `aic_init()` reads the AIC version and base address.
- `aic23_init()` reads `aic-iack-offset`, `cap0-offset`, `maxnumirq-offset`.
- `aic_mask_set` / `aic_mask_clr` control interrupt masking.
- `aic_ack()` reads the event register.

Windows port:
- A boot or HAL-extension component reads the same offsets from ACPI/DT-derived data.
- `AicInit()` stores the base and version.
- `AicMaskAll()` writes to `AIC_MASK_SET`.
- `AicAcknowledge()` reads the event register.
- Interrupt delivery is routed through b00t's virtual GIC in Phase 1.

### DART

Asahi:
- DART domains are configured per device.
- 16 KiB page tables and stream IDs.

Windows port:
- b00t owns DART domains initially.
- A storage miniport uses 16 KiB-aligned buffers.
- No IORT is exposed until the model is proven.

### NVMe

Asahi:
- Controller discovery and admin queue setup.
- PRP lists and DMA buffers.

Windows port:
- `NvmeInit()` discovers the controller.
- `NvmeMapPrp()` enforces 16 KiB alignment.
- A storport miniport forwards requests or owns the queue pair.

### USB

Asahi:
- DWC3 initialization and PHY/PD sequencing.

Windows port:
- Prefer inbox xHCI if ACPI describes the controller.
- Custom driver handles PHY/PD/role if needed.

### PCIe

Asahi:
- Host bridge and port initialization.

Windows port:
- ACPI `_CRS` and `_DSD` describe resources.
- Windows inbox PCIe drivers bind where possible.

### PMU/SMC

Asahi:
- Battery, thermal, charger, and fan control.

Windows port:
- WDF driver reads sensors and enforces thermal limits.
- Fan control stays conservative.

### DCP

Asahi:
- Display controller initialization.

Windows port:
- Phase 1-3 use the simple framebuffer.
- Phase 4 implements a display-only WDDM driver.

## Validation

For each ported driver:

1. Identify the Asahi source and hardware block.
2. Build a Windows skeleton that logs initialization.
3. Add ACPI descriptions.
4. Test in Windows PE or a full install.
5. Stress I/O, reset, and power transitions.
6. Document unsupported features and known limitations.
